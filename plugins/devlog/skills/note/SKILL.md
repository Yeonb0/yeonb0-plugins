# devlog : 세션 기록

블로그 개발일지에서 가장 쓰기 어려운 부분은 "왜 그렇게 결정했는가"이다. 커밋에는 무엇을 바꿨는지만 남고, 이유는 대화 속에만 있다가 사라진다. 이 스킬은 세션이 끝날 때 그 이유를 짧은 기록으로 저장소에 남긴다.

## 인자

- `[메모]` : 자유 텍스트. 있으면 같은 Phase의 `notes.md` 끝에 날짜와 함께 덧붙인다.
- `--phase N` : 기록할 Phase. 없으면 설정의 `current_phase`.

## 절차

1. **대상 저장소와 설정 찾기.** 현재 작업 중인 프로젝트 저장소를 정한다 (로컬 작업 트리의 origin, 대화에서 언급된 저장소, 그래도 모르면 한 번 묻기). `.devlog/config.yml` 을 읽는다. 없으면 `references/config.md` 의 첫 실행 설정을 진행한 뒤 이어서 한다. 저장소 읽기 · 쓰기 방법은 `references/repo-access.md` 를 따른다.

2. **세션 요약 작성.** 이번 대화 전체를 훑어 아래 네 섹션으로 정리한다. 대화에 없는 내용을 지어내지 않는다. 해당 내용이 없는 섹션은 "없음"으로 둔다.
   - 결정 : 무엇을 하기로 했는가 (구현 방식, 라이브러리, 구조, 범위 조정)
   - 이유 · 버린 대안 : 왜 그쪽을 골랐고 무엇을 왜 버렸는가. 개발일지의 핵심이므로 가장 공들여 쓴다
   - 막힌 점 : 에러, 오해, 시간이 오래 걸린 지점과 해결 방법
   - 다음에 할 일

3. **민감 정보 거르기.** 블로그 재료가 되므로 아래를 지우거나 일반화한다.
   - 토큰 · API 키 · 비밀번호 · `.env` 값 · 접속 주소의 자격 증명
   - 로컬 절대 경로 (`C:\Users\...`, `/home/<이름>/...`) → 저장소 기준 상대 경로로
   - 프로젝트와 무관한 사적인 대화, 다른 사람의 개인 정보
   - 학교 과제라면 다른 학생 이름 · 학번

4. **미리보기 확인.** 거른 요약을 사용자에게 보여주고 "이대로 저장할까요?"라고 묻는다. 고쳐 달라고 하면 반영해서 다시 보여준다. 이 단계는 건너뛰지 않는다 (민감 정보를 사람이 마지막으로 보는 지점).

5. **저장.** 아래 경로에 쓰고 기본 브랜치에 커밋한다. 메모 인자가 있으면 `notes.md` 도 같은 커밋에 넣는다.
   - `docs/devlog/phase-<N>/sessions/<YYYY-MM-DD>-<surface>-<slug>.md`
   - `<surface>` 는 `cli`, `cowork`, `claude-ai` 중 현재 환경. `<slug>` 는 결정 내용에서 뽑은 짧은 한글 · 영문 구절 (하이픈 연결, 30자 이내)
   - 같은 이름이 있으면 `-2` 를 붙인다
   - 커밋 메시지 : `docs(devlog): phase <N> session note`

6. **결과 알림.** 저장한 경로 한 줄. 이번 Phase의 완료 기준이 충족된 것처럼 보이면 `/devlog:publish` 를 제안한다 (실행은 하지 않는다).

## 세션 요약 파일 형식

```markdown
---
date: 2026-11-06
surface: cowork
phase: 3
---

## 결정

## 이유 · 버린 대안

## 막힌 점

## 다음에 할 일
```

## 저장할 수 없을 때

로컬 작업 트리도, `gh` 도, GitHub 커넥터도 없으면 (예 : 커넥터가 연결되지 않은 claude.ai 채팅) 위 형식의 요약을 코드 블록으로 보여주고, "GitHub 커넥터를 연결하거나, 이 요약을 Cowork에서 `/devlog:note` 와 함께 붙여 넣으면 저장할 수 있습니다"라고 안내한다. 이 경우에도 3 · 4단계는 똑같이 한다.
